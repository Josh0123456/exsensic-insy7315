# Exsensic shared UI components

All files in this guide are relative to `src/Exsensic.Web`. Models live in `Models/Shared`; partials live in `Views/Shared`. Use MVC's partial tag helper with a typed model. Do not copy component markup into feature screens.

## Shared conventions

- Global CSS: Bootstrap, `wwwroot/css/tokens.css`, then `wwwroot/css/site.css`. The palette is charcoal with restrained lime accents; spacing, type, radius and shadow scales remain shared.
- All text is Razor-encoded. Pass plain text, never HTML. No inline styles, fonts or external libraries.
- Link fields accept local URLs only, generated by the parent controller/view using `Url.Action` or routing. The caller must supply an implemented destination. Optional actions require both text and URL. Mutations belong in POST forms, never these links.
- Use one PageHeader (h1) per page. Place service/booking cards and empty states (h3) beneath a section heading (h2).
- Dates and times are already converted by the caller to the intended display time zone. Prices are optional decimal values displayed in South African rand; null omits the price, zero displays R 0.00.
- Components decide presentation only. Permissions, status transitions, availability, pricing and API/database work remain outside these models/partials.

### Booking status dependency

The Web project references Contracts, but Contracts currently has **no BookingStatus enum implementation**. StatusBadgeViewModel.Status and BookingCardViewModel.BookingStatus therefore use required strings temporarily. The badge's explicit display mapping accepts only the four exact contract names and throws for unsupported input; it never silently relabels unknown values. No duplicate enum or business rules were added. Once Contracts supplies `Exsensic.Contracts.Enums.BookingStatus`, replace these two property types and the badge switch with that shared enum. Do not add Pending, Rejected or Rescheduled.

### Pager

Supply 1 <= CurrentPage <= TotalPages. For an empty collection, use EmptyState and TotalPages = 0 (pager is omitted). At the first/last page or when a local URL is missing, controls are native disabled buttons without hrefs. URLs should retain caller-owned query filters. Use a distinct Label if two pagers appear on one page.

### Feedback

Set `TempData[ToastKeys.Success]` (`Ui.SuccessMessage`) or `TempData[ToastKeys.Error]` (`Ui.ErrorMessage`) to plain text. The layout renders _Toasts once and consumes each key once. Both may appear together. Text labels identify success/error in addition to colour. The container uses role=status, aria-live=polite and aria-atomic=true. Messages remain visible; no timed dismissal. Screen-reader announcement of server-rendered initial content varies, so messages are also readable in the page's main content.

### Confirmation dialog

Render the partial once per unique dialog ID. Use a CSS-selector-safe HTML ID without spaces.

For a confirmation-only interaction, use a `type="button"` trigger with `data-confirm-dialog="your-dialog-id"`. Confirmation dispatches the bubbling `ui:confirmed` event on that trigger; the caller may handle it. Nothing navigates or mutates automatically.

For a future server action, put `data-confirm-dialog` on a native `type="submit"` button in the caller's POST form (with the normal MVC antiforgery token). The script intercepts the valid submit, opens the dialog, and only on confirmation replays `requestSubmit` with that original button, preserving its name/value and form validation. Cancel and Escape never submit. Missing dialogs fail closed for intercepted submissions. Confirmation does not replace server authorization or validation. Normal form behaviour applies when JavaScript is unavailable.

The native modal dialog contains keyboard focus; initial focus is on the safe cancel action. Closing restores focus to the originating trigger. Both controls are explicit buttons. The partial contains no nested form.

### Slot picker

`SlotPickerViewModel.Dates` is a list of `SlotDateViewModel` (Date, IsAvailable, Slots). Each `SlotOptionViewModel` has Id, StartTime, optional EndTime, IsAvailable and optional UnavailableReason. Supply dates and slot IDs without duplicates and display times in the stated TimeZoneLabel.

The selected enabled date is shown, falling back to the first caller-enabled date. Only an enabled slot on that date may be initially selected. Date buttons expose aria-pressed plus the word Selected. Radio inputs have explicit labels inside a fieldset with a date-specific legend. Unavailable choices have text and native disabled controls. Empty dates/slots have explanations.

The small script switches existing date panels and clears the previous radio choice; hidden date fieldsets are disabled and cannot submit stale values. Supply a distinct InputName for each picker in the same form. The picker creates no form, fetches nothing and computes no availability. Without JavaScript the initial date's radios remain usable, but date switching requires JavaScript. The parent screen must validate a submitted selection and any later API availability response.

## Reuse example

Inside an existing page beneath its h2 section heading:

```cshtml
<partial name="_EmptyState" model="@(new EmptyStateViewModel {
    Title = "No bookings yet",
    Message = "Your bookings will appear here once you request a service."
})" />
```

No production showcase or invented feature routes are required. New screens must supply their own data and real local destinations.
