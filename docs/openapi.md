# OpenAPI specification: how it is published

Decision record for the marker's request for an API description outside Development. Owner: Daniel (P2).

## Decision

The API description is **published as a file, `docs/openapi.json`, committed to the repository and
checked by the integration tests**. The running API serves **no** OpenAPI endpoint outside Development.

| Environment | Where the spec is |
|---|---|
| Development | `GET /openapi/v1.json` (anonymous, local machine only, as before) |
| Staging, Production, CI | `docs/openapi.json` in the repository. Nothing is served by the deployed API |

## Why not a live endpoint on the deployed API

- An anonymous `/openapi/v1.json` would let anyone map every admin and staff operation. The file in the
  repository tells the reader the same thing without giving an attacker a live, always-current map of the
  production API.
- Protecting a live endpoint (admin token, or an IP allow-list) would need new hosting and authorisation
  rules in the API, and an admin token cannot be used by a marker or a reviewer opening a browser.
- The API is restricted to the web app's outbound IPs (CONTRACTS section 12, decision 12). A live endpoint
  would have to be reachable by a reader too, which weakens that restriction. A file in the repository
  doesn't touch it.

## How the file stays accurate

The spec is generated by the same `AddOpenApi` code that Development uses, from the real controllers
and their attributes. `OpenApiSpecTests` (integration tests) then:

1. Lists every controller route from the running app and checks the spec has exactly those operations.
2. Checks the only operations without a security requirement are the six anonymous ones in CONTRACTS
   section 6, and that every `/admin/` operation requires a token and names the Admin role.
3. Checks the spec holds no signing key, connection string, password or server address.
4. Compares the generated spec with `docs/openapi.json`. **If a route, DTO or attribute changes and the
   file isn't updated, CI fails** with an "out of date" message.
5. Checks the live spec endpoint is not served outside Development (404 for a signed-in admin, 401 or 404
   for an anonymous caller).

## Updating the file

After changing a controller or DTO, regenerate the file and commit it:

```bash
EXSENSIC_UPDATE_OPENAPI=true dotnet test tests/Exsensic.IntegrationTests --filter "FullyQualifiedName~OpenApiSpecTests"
```

PowerShell: `$env:EXSENSIC_UPDATE_OPENAPI = "true"` first, and remove it afterwards.

## What the spec contains and leaves out

- Contains: routes, parameters, request and response shapes, the JWT bearer scheme, and for each
  operation the role or policy it needs ("Access: ...").
- Leaves out: server URLs (the API's host and IP rules are not part of the contract), secrets, and any
  seed or demo account.
- The spec does not yet list every error response (400, 401, 403, 404, 409, 429). Those are described in
  CONTRACTS section 7 and are checked by the contract-consistency work.

## For Josh (hosting)

Nothing in `.github/` or the hosting settings changes. If the team later wants CI to attach the file as a
build artifact, upload `docs/openapi.json` from the existing `build-test` job: the tests already prove it
matches the build.
